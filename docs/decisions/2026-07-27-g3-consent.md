# G3: consent, and the half of erasure we can actually do

**Date:** 2026-07-27
**Status:** partial, and deliberately so
**Touches:** new `@gt100k/consent`, `guide-console`'s ingest route

## Why now

The roadmap has listed G3 as a gate that blocks live use since before there was anything to gate.
There is now: the discovery game can post a real session to the console. That capability is reachable
only by setting `VITE_GT100K_INGEST_URL`, which nobody sets, and an unset environment variable is a
decision about defaults rather than a consent regime.

## What this is

Consent is **per purpose**. A guardian agreeing that a guide may read their child's interests has not
agreed that the child's work may be shown to a stranger, and a single yes covering every future use
is exactly what purpose limitation exists to prevent. Four purposes: discovery measurement, guide
review, family coaching, external audience.

It **denies by default and in every ambiguous case**. A missing consent file means no consent, not
"not configured yet"; an unparseable date denies rather than being skipped. The asymmetry decides
this: a wrong no shows a guide a blocked banner, a wrong yes collects a child's data without
permission.

**Withdrawal is absolute** and is checked before anything else, including before whether the withdrawn
record covered the purpose being asked about. It is recorded rather than deleted, because a
withdrawal is itself a fact worth keeping, and it is not undone by a second grant sitting on file.

**Consent does not last forever.** A year unreviewed produces `stale-needs-review` rather than a
silent continuation, with a warning thirty days ahead so the review lands before the block does.

## What this is not

It does **not** verify that a guardian is who they say they are. Verifiable parental consent under
COPPA is a process involving an identity signal this repository has no access to, and a checkbox
claiming to be one would be worse than the current absence. So `ConsentMethod` records *how* consent
was obtained: `guide-asserted` is a guide typing that a parent said yes, it is what a pilot will
actually have, and it is kept as its own value precisely so a stricter policy can refuse it later
without every existing record having to be reinterpreted.

## Erasure is two problems with one name

**The half that is solved.** A `StudentProfile` is a JSON file per child. Its log is append-only as a
discipline, not as a cryptographic commitment: nothing references those records by content, no id is
derived from them, and deleting the file leaves nothing dangling. Erasure there is deletion and it
can be complete.

**The half that is not.** The EvidenceGraph is content-addressed. A node's id *is* the hash of its
content and edges reference those ids, so deleting a node breaks the edges pointing at it, and the
surviving ids leak the shape of what went. That is E1's D2, the hardening docs name it unsolved, and
it is not this package's to fix.

`eraseEverywhere` therefore reports `unerased` by name. A guardian is told which stores still hold
their child's data rather than shown a green tick over the one that does. One store failing never
stops the others, because partial erasure beats none.

This is also why the ingest path built alongside this deliberately does not feed the graph. A child's
discovery record is erasable today; their project evidence is not, and that gap is the reason the
gate stays shut rather than a reason to pretend it is open.

## What still blocks live use

- No identity verification, per above. `guide-asserted` is the strongest thing a pilot can honestly
  claim.
- No UI. Consent lives in a `consent.json` beside the profiles, which is fine for one guide on one
  machine and nothing else.
- EvidenceGraph erasure, E1 D2.
- The ingest route has no authentication or rate limiting.
- Retention is a review prompt, not enforced deletion. Nothing yet deletes a profile when its consent
  goes stale; `eraseEverywhere` exists and is called by no schedule.
  **Sharper, checked 2026-07-28:** it is not only unscheduled. `ErasableStore` has no implementation
  anywhere outside `erasure.test.ts`, so neither the profile store nor the graph is wired to it and
  the solved half of erasure is solved on paper. The withdrawal path is in the same position —
  `withdraw` is exported and nothing calls it, so a guardian taking consent back means someone editing
  `consent.json` by hand.
